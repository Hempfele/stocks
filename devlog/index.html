2026-06-13 · night

Where the data lives, and who holds the keys

Before inviting player 2, we wrote down how trust actually works in this game — the full reference is SECURITY.md in the repo; this is the story version.

GitHub Pages is not a backend. It serves the same static files ./play.sh serves from localhost — HTML, CSS, JavaScript, and one committed key. All real data lives in exactly one place: a Postgres database at Supabase (eu-west-1, Ireland). Whether the game runs on Pages or locally, your browser talks straight to that database over HTTPS. The only real difference between live and local is the URL in the address bar — which is why both origins sit in the magic-link redirect allow list.

The committed key is supposed to be public. js/config.js openly carries the anon key — Supabase calls it "publishable" because it grants only what row-level security allows, and for a stranger that is nothing at all: every table denies anonymous access. Signed-in players can read the whole game (seeing each other's picks is the game) but write only their own name. The dangerous key — the service role, which bypasses RLS — exists only inside Supabase's edge-function runtime. It has never been in the repo and never reaches a browser.

Locked means locked, says Postgres. No player can write a pick directly. The only path is the make-pick function: verify who you are, check the season is active, fetch the live quote server-side, insert. No update policy, no delete policy, one pick per area by unique constraint. Honesty isn't a UI feature here; it's a database constraint.

The one honest gap: until "allow new sign-ups" is switched off, anyone with the URL could join and watch. The fix is one toggle, flipped after both players are in. And the threat model stays humble — this protects a friendly game from accidents and cheating, not from someone who controls your email inbox. No real money ever moves.

Addendum: local testing became one command — ./play.sh demo (offline, fake data, even with live config thanks to a ?demo override), ./play.sh fresh (blank slate), ./play.sh (live backend).

2026-06-13 · later that day

The database gets a memory

Second session: we talked through the database before going live. The trust model held up under discussion — anon key public by design, RLS for reads, picks writable only by the make-pick edge function — but one gap surfaced: prices only kept the latest quote, throwing the past away. So the schema grew price_snapshots: one closing price per symbol per day, fed automatically by both edge functions. Cheap now, impossible to backfill later; it also gives past seasons frozen final standings for free.

Go-live is half walked: the Supabase project exists (the region note was later corrected to eu-west-1, Ireland), the CLI is installed, and the next session starts with supabase login → link → push → deploy. The checklist lives in CLAUDE.md under "Current status".

2026-06-13

From a voice note to a playable scaffold

The game started as a six-minute voice memo recorded on the Desktop. A new reusable /transcribe skill (local whisper, afconvert → 16 kHz WAV) turned it into a transcript; from there came PLAN.md, two explicit architecture decisions, and by the end of the session a fully playable game in demo mode: sign in, name yourself, pick stocks for ten life areas via typeahead search, lock them in, and watch the dashboard compare players — crown included.

Supabase is fully prepared but not yet live: 001_init.sql (schema + RLS) and three edge functions (stock-search, make-pick, refresh-prices) sit in the repo, with the go-live checklist in README.md.
