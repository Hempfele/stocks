Decisions

The durable choices behind Fantasy Portfolio: how it is built, what it protects, and what we deliberately keep out so the game stays lightweight.

Technical

The architectural choices that make the game playable, trustworthy, and easy to host.

  • GitHub Pages + Supabase — static frontend, free tier auth/Postgres/edge functions; reachable by a remote player 2. 2026-06-13
  • Magic-link email auth — no passwords, real accounts, scales to more players. 2026-06-13
  • Yahoo Finance via edge functions — US + EU coverage, no API keys in the client, no CORS. 2026-06-13
  • Server-side pick locking — make-pick fetches the quote and inserts; RLS keeps clients read-only on picks. 2026-06-13
  • Ratio-based scoring — €1,000 × current/locked; mixed currencies compare fairly. 2026-06-13
  • Demo mode — empty config runs the full game on fake data. 2026-06-13
  • Daily price snapshots — price_snapshots keeps one close per symbol per day; history can't be backfilled later. 2026-06-13

Do's / Don'ts

The working rules and tradeoffs that keep the project small, honest, and in the right spirit.

Do's

  • Voice first. Ideas arrive as voice notes; /transcribe turns them into local transcripts.
  • Plan, then build. Big choices get asked as explicit either/or questions before code.
  • Demo mode is the test bench. Verify locally with ?seed and ?reset.
  • Local preview stays simple. ./play.sh demo or python3 -m http.server; GitHub Pages once live.
  • Maintain the devlog. End each session with a dated entry, decisions, and a screenshot when visual.
  • SECURITY.md stays the canonical reference for keys, storage, and policies.
  • Say plainly that magic-link identity = inbox control; that's the trust anchor.
  • Pilot Season (~7 weeks) over a full quarter — test the rules before committing.
  • Seed seasons via migration — reproducible, versioned, no secrets in shell history.
  • Close public sign-ups in Supabase once both players are in.

Don'ts

  • Raspberry Pi hosting — local-only; awkward for a remote second player.
  • Player codes / Google OAuth — magic links won on friction vs. realness.
  • FX conversion — unnecessary once scoring is ratio-based.
  • Charts & analytics — against the spirit; numbers stay quiet.
  • A build step / framework — vanilla modules keep deploys trivial and the code legible.
  • Yahoo dependency denial — the unofficial API is fine for a friendly game, but replaceable only at the edge-function layer.
  • Notification decisions too early — email vs Telegram waits until the game is live.
  • Don't pretend the anon key is a secret — rotating or hiding it adds nothing once RLS does the work.
  • Don't use a stricter threat model than the project needs — proportionality: it's a game between friends, not a bank.
  • Don't script dashboard-only steps with borrowed credentials — two honest browser clicks instead.
  • Don't add a frozen "final value" column on seasons — snapshots reconstruct it.
  • Don't build in-game season administration yet — Season 1 gets seeded by hand.
  • Don't lock prices client-side — too forgeable, even among friends.
